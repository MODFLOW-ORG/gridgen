\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

GRIDGEN is a computer program for creating layered quadtree grids for use with numerical models, such as the MODFLOW-USG program \citep{modflowusg} for simulation of groundwater flow. The program begins by reading a three-dimensional base grid, which can have variable row and column widths and spatially variable cell top and bottom elevations. From this base grid, GRIDGEN will continuously divide into four any cell intersecting user-provided refinement features (points, lines, and polygons) until the desired level of refinement is reached. GRIDGEN will then smooth, or balance, the grid so that no two adjacent cells, including overlying and underlying cells, differ by more than a user-specified level tolerance. Once these gridding processes are completed, GRIDGEN saves a tree structure file so that the layered quadtree grid can be quickly reconstructed as needed. Once a tree structure file has been created, GRIDGEN can then be used to (1) export the layered quadtree grid as a shapefile, (2) export grid connectivity and cell information as ASCII text files for use with MODFLOW-USG or other numerical models, and (3) intersect the grid with shapefiles of points, lines, or polygons, and save intersection output as ASCII text files and shapefiles. The GRIDGEN program is demonstrated by creating a layered quadtree grid for the Biscayne aquifer in Miami-Dade County, Florida, using hydrologic features to control where refinement is added. Layered quadtree grids created by GRIDGEN can also be used with MODFLOW~6 \citep{modflow6gwf}.

Version numbers for GRIDGEN will follow a major.minor.revision format. The major number will be increased when there are substantial new changes that break backward compatibility. The minor number will be increased when important, but relatively minor new functionality is added. The revision number will be added when errors are corrected in either the program or input files.

The arrays written by the GRID\_TO\_USGDATA block also define the unstructured discretization (DISU) input for MODFLOW~6. The connection direction (fldr) gives the connection type (IHC), and the connection lengths (c1 and c2) give CL12. The connection area (fahl) gives HWVA for a vertical connection; for a horizontal connection, HWVA is fahl divided by the average thickness of the two connected cells. A layered quadtree grid with the same horizontal grid in every layer can also be represented with the discretization by vertices (DISV) input, using cell vertices from the grid shapefile.

\section{Distribution}

GRIDGEN is distributed as assets of each release of the GRIDGEN repository on GitHub (\url{https://github.com/MODFLOW-ORG/gridgen/releases}):

\begin{itemize}
  \item linux.zip, macarm.zip, and win64.zip---the GRIDGEN executable for Linux, macOS on Apple silicon, and 64-bit Windows
  \item gridgen\_source.zip---the source code, build files, and test problems
  \item ReleaseNotes.pdf---this document
\end{itemize}

The GRIDGEN report \citep{lien2015gridgen} documents the input and output of the program.

\section{Installation}

There is no installation of GRIDGEN other than unzipping the archive for your operating system into a location where it can be accessed. To make GRIDGEN accessible from any directory, add the directory containing the executable to the PATH environment variable, and remove the directory of any prior GRIDGEN release from the PATH.

GRIDGEN can also be installed with the get-modflow program distributed with FloPy 3.12 or later, which downloads the executable for the current operating system from the latest GRIDGEN release:

\begin{verbatim}
get-modflow --repo gridgen /path/to/bin
\end{verbatim}

\section{System Requirements}

GRIDGEN is written in C++. Executables are built and tested for Linux, macOS, and Windows; the source code can be compiled on other operating systems with a C++ compiler.

\section{Executing GRIDGEN}

GRIDGEN is run from a command prompt or terminal by entering ``gridgen'' followed by an action and the name of the definition file that contains it, for example ``gridgen buildqtg action01\_buildqtg.dfn''. Actions and definition files are described in the GRIDGEN report.

\section{Testing}

The test problems are in the test directory of the source code. From the source code archive (gridgen\_source.zip), ``meson setup builddir -Dunit\_tests=enabled'', ``meson compile -C builddir'', and ``meson test -C builddir'' build GRIDGEN and run the test problems, unit tests, and a check that repeated runs produce identical output. In a clone of the GRIDGEN repository, the pixi package manager (\url{https://pixi.sh}) provides the same steps as ``pixi run setup'', ``pixi run build'', and ``pixi run test''.

\section{Compiling}

GRIDGEN is compiled with the Meson build system and a C++ compiler. From the root of the source code archive, ``meson setup builddir'' and ``meson compile -C builddir'' build the executable in builddir/src; in a clone of the repository, ``pixi run setup'' and ``pixi run build'' configure the build and install the executable in the bin directory. However, the USGS cannot provide assistance to those compiling GRIDGEN.

\section{Test Problems}

The following test problems are in the test directory of the source code archive (gridgen\_source.zip).

\begin{itemize}
  \item Biscayne aquifer test problem -- The definition files action01\_buildqtg.dfn through action05\_vtkfile.dfn build a layered quadtree grid for the Biscayne aquifer in Miami-Dade County, Florida, and write USG data, shapefiles, intersections, and VTK files. This test problem is described in \citet{lien2015gridgen}.
  \item Additional regression cases -- action06\_buildqtg\_multilayer.dfn and action07\_multilayer.dfn build a three-layer grid with point refinement set by a shapefile attribute, interpolated elevations, vertical pass-through, vertical ghost nodes, and point and polygon intersections; action08\_buildqtg\_rotated.dfn and action09\_rotated.dfn build a rotated grid. Both use the inputs of the Biscayne aquifer test problem.
\end{itemize}

\section{Tips and Recommendations}

\begin{enumerate}
  \item Getting started---The best way to get started with GRIDGEN is to run the Biscayne aquifer test problem (action01\_buildqtg.dfn through action05\_vtkfile.dfn in the test directory of gridgen\_source.zip). The test problem demonstrates the sequence of steps for generating a grid, intersecting the grid, and for writing grid shapefiles, MODFLOW-USG discretization input, and VTK files. The example files for GRIDGEN can then be used as a starting point for creating new applications.
  \item Vertical refinement considerations for MODFLOW-USG and MODFLOW~6 models---Testing with multi-layer models that have quad-based refinement has revealed oscillatory flow paths for some hydrogeologic conditions. These oscillatory flow paths are inconsistent with expected flow paths, and do not occur when the same horizontal grid is used for each layer. One cause is that the center of a cell is not above or below the centers of the smaller cells it connects to in the layer above or below it. With the record GNC\_VERTICAL = True, which the GRIDGEN report does not describe, a GRID\_TO\_USGDATA block also writes a ghost node for each such vertical connection, after the horizontal ghost nodes and in the same format in the .gnc.dat file. The ghost node is in the larger cell, below or above the center of the smaller cell, and its head is interpolated from the larger cell and its neighbors on the side of the smaller cell in the x and y directions, so that a head that varies linearly in x and y is reproduced. Where one of those neighbors is missing, at the edge of the grid or because it is inactive, the other direction alone is used, and no ghost node is written where both are missing. With VERTICAL\_PASS\_THROUGH = True, the vertical connections across inactive cells also get ghost nodes. GNC\_VERTICAL = True is ignored, with a warning, for a MODFLOW grid. In MODFLOW~6 and MODFLOW-USG tests of a three-layer grid with different refinement in each layer and flat layers, with heads varying linearly over 86 length units, adding the vertical ghost nodes to the horizontal ones reduced the largest head error from 1.3 to 0.014 length units; the remaining error is from the horizontal ghost nodes (see Known Issues). The vertical ghost nodes can improve the simulated flow paths, but they have not been tested for the oscillations described above, so the recommendation remains to use the same horizontal grid for all layers of a model where practical. This is achieved with GRIDGEN by listing the same set of refinement features for each model layer.
  \item Grid specification files---A GRID\_TO\_GSF block, which the GRIDGEN report does not describe, writes a MODFLOW-USG grid specification file of the kind read by the PEST Groundwater Utilities (\url{http://www.pesthomepage.org/Groundwater_Utilities.php}). The record GRID names the grid and GSF\_FILE the file to write. Each active cell is listed with its node number, the x, y, and elevation of its center, its layer, and its vertices: the four corners at its top and the same four at its bottom. With the optional record HANGING\_VERTICES = True, the vertices of a cell also include the corners of smaller cells beside it in the same layer that lie on its edges; the default, False, lists only the eight corners that the PEST programs USG2VTK and USGQUADFAC require. Vertex elevations are interpolated from the tops and bottoms of the cells that share each vertex, as in a VTK file written with SHARE\_VERTEX = True, and inactive cells and the vertices used only by them are left out. Node and vertex numbers start at 1 whatever the NODE\_NUMBERING of the grid, as MODFLOW-USG requires. The optional record NODE\_DATA\_TABLE\_FILE names a file that lists, on one line per active cell, its node number and the layer, row, and column of the base grid cell that contains it. Coordinates are written to full precision, whereas the GRIDGEN2GSF program of the PEST Groundwater Utilities, which writes a grid specification file from the tree structure file, rounds them to three decimal places and lists no vertices on cell edges.
  \item Vertices for MODFLOW~6---A GRID\_TO\_USGDATA block also writes two files that the GRIDGEN report does not describe: a file ending in .vertices.dat with the number and the x and y coordinates of each vertex, and a file ending in .cell2d.dat with, for each active cell, its node number, the x and y coordinates of its center, its number of vertices, and the numbers of those vertices in clockwise order. Their lines are the records of the VERTICES and CELL2D blocks of the MODFLOW~6 DISU Package; when every layer has the same cells, the vertices and the CELL2D lines of the first layer are also the VERTICES and CELL2D blocks of the DISV Package. Each cell lists the corners of smaller cells beside it in the same layer that lie on its edges, so that MODFLOW~6 connects the cell to each of them. As in the .nod file, node and vertex numbers start at 1 whatever the NODE\_NUMBERING of the grid.
  \item Connection count in the .nod file---GRIDGEN writes a file with a ``.nod'' extension when a GRID\_TO\_USGDATA block is executed. The first line in the .nod file has the number of cells and the number of connections. The number of connections does not include values for the node itself, and so this value does not directly correspond to the NJA value required by MODFLOW-USG. Instead, this value is equal to NJA - NODES.
  \item Closing cell polygons in shapefiles---A GRID\_TO\_SHAPEFILE block with FEATURE\_TYPE = polygon writes each cell as a polygon that ends with its first vertex, as the shapefile specification requires. The optional record CLOSE\_POLYGONS, which the GRIDGEN report does not describe, controls this: True, the default, closes each polygon, and False writes the four corners of each cell without repeating the first. A shapefile written with CLOSE\_POLYGONS = False does not follow the specification, and programs that read shapefiles with GDAL report its polygons as not closed. CONCIDE, the previous name of the record, is still read but is deprecated.
  \item Using GRIDGEN with FloPy---The Gridgen class of FloPy \citep{bakker2016flopy, hughes2023flopy} runs GRIDGEN and uses its output to create MODFLOW-USG input (\texttt{get\_disu}, \texttt{get\_gridprops\_disu5}, and \texttt{get\_gridprops\_gnc5}) and MODFLOW~6 input (\texttt{get\_gridprops\_disu6}, \texttt{get\_gridprops\_disv}, and \texttt{get\_gridprops\_gnc6}), and to intersect points, lines, and polygons with the grid (\texttt{intersect}).
\end{enumerate}

\section{Known Issues}

The following defects are known in this version. Each is tracked as an issue on GitHub (\url{https://github.com/MODFLOW-ORG/gridgen/issues}) and is removed from this list when it is fixed.

\begin{itemize}
  \item A horizontal ghost node in the .gnc.dat file does not reproduce a head that varies linearly when the only cell it is interpolated from is larger than the cell that contains the ghost node and offset along the connection, so the flow between the two connected cells is slightly in error. In a three-layer test grid this was the case for about 4 percent of the horizontal ghost nodes (\ghissue{161}).
  \item With VERTICAL\_PASS\_THROUGH = True, a cell above or below an inactive cell that is larger than it is connected to every active cell on the other side of the inactive cell, including cells that are not below or above it, and each of these connections is given the area of the smallest cell in the column rather than the area the cells share. No ghost node is written for a connection between cells that do not overlap (\ghissue{163}).
\end{itemize}
